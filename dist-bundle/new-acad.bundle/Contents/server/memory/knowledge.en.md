# new-acad Built-in Knowledge Base (Precondition Checks + Cautions)

> Purpose: for complex tasks, read this first to verify preconditions, then organise the steps on the spot based on what the user actually says.
> ⚠️ Design principle (set by Bro, 2026-08-07): **No fixed step templates** — users' natural language is often imprecise ("selected" may mean nothing is selected; a "boundary line" may be a different layer). Fixed flows tempt the AI to copy them blindly and fail. The AI organises the flow from the actual conversation; this knowledge base only provides: precondition checks + cautions.
> Method lookup: `listMethods` with a filter (e.g. filter="surface"). Common methods carry their own descriptions. Never guess method names.

## 1. Key Precondition Checks (concise, 2026-08-08)

> Verify before acting; if something doesn't match, say so honestly. **Do not teach per-scenario judgement — for complex tasks follow the injected plan.**

0. **"What's in the drawing / vague instruction / whole-drawing overview"** → first call `getDrawingOverview` (units / layers+counts / blocks+counts / type distribution / selection count)
1. **"selected / these"** → first call `getSelection` to confirm something is actually selected; if not → tell the user to box-select
2. **"export / generate a file"** → first confirm path and format (user-facing coordinates → csv/txt; for the AI's own use → json)
3. **Uncertain numeric parameters** (radius vs diameter, etc.) → use common sense; if unsure, ask

## 2. Cautions (concise)
- Unsure of a method name → `listMethods` with a filter (never brute-force guess names)
- **Supported/unsupported is decided at runtime**: filter → reword and query again → still nothing → report [MISSING] with alternatives
- Large results are truncated (≤2KB) → for full data switch to the file channel (export / read file)
- Command-style methods such as `executeCommand`/`runLisp` and fillet/chamfer/trim/extend/stretch return `{status:"queued"}` (async dispatch, no synchronous result) — **this does not mean failure**
- **`loftSolid` is now a real API** (2026-08-11: LoftedSurface+Thicken chain, returns solidHandle synchronously; params: crossSections ≥2 closed curves + optional guides/path/ruled/closed/draftStart/draftEnd/thickness=1/bothSides; the result is a **thin shell solid**; a truly solid body needs the LOFT command as fallback)
- **NURBS free-form surface trio** (added 2026-08-11): `createNurbsSurface{uCount,vCount,points:[[x,y,z]...]}` → `editNurbsControlPoints{handle, points|moves}` → `thickenSurface{handle,thickness,bothSides?}`; smooth surface → thicken into a thin shell
- **Create a corridor** (added 2026-08-16): `createCorridor{corridorName, alignmentName, assemblyName, baselineName?, regionName?, startStation?, endStation?, profileName?, surfaceName?, style?}` — alignment + assembly → corridor; profileName optional (vertical reference), surfaceName optional (auto-link a surface); query style with listStyles filter='corridor'
- **One-click add corridor surface (for quantity take-off)** (added 2026-09-11, fixed 2026-09-21): `addCorridorSurface{name, surfaceName?, codes?[], asBreakLine?, waitForBuild?=true}` — attaches the corridor's **link codes** as surface data and builds the surface; **runs via the job channel** (returning `{jobId, state:"running"}` is normal; poll with `getJobStatus{jobId}`). **Default `waitForBuild=true`: the job returns only after the surface is truly built (quiet-window strategy, ~90s measured), and reports `buildReady`/`waitedMs`**; meanwhile other requests get `JOB_RUNNING` (relay auto-retries), and CAD is immediately usable once the job finishes. `waitForBuild=false` = returns instantly (CAD still busy ~1 min right after, result uncertain). **Implementation note**: the write transaction goes through `App.Idle` (not a command context), otherwise C3D throttles it to 215–360s with ~half false failures; **do not poll the document every 2s** — it starves C3D's async regeneration. If you don't pass `codes`, they are **auto-collected**; `surfaceId` in the result = the surface object handle; also `addedLinkCodes / isBuild / surfaceCount`. **You must call this to get a surface / quantity** (a corridor from createCorridor has no surface data by default, surfaceCount=0). Precondition: custom-part **links** must carry codes — shape codes go only into material tables, not surfaces.
- **Style / label-set edits** (added 2026-08-16):
  - `setAlignmentStyle{alignmentName, style?, labelSet?}` — change an existing alignment's style/label set; query style with `listStyles{objectType:'alignment'}`, labelSet with `listStyles{objectType:'alignmentlabelset'}`
  - `setProfileStyle{alignmentName, profileName, style}` — change an existing profile style; query with `listStyles{objectType:'profile'}`; **a profile label set can only be set at creation**; to change the set use setProfileViewStyle
  - `setProfileViewStyle{profileViewName, style?, bandSet?}` — change a profile-view style/band set; **Chinese-style profile = swap band set (bandSet) + view style**; query with `listStyles{objectType:'profileview'}` and `listStyles{objectType:'profileviewbandset'}`
- **listStyles supported types**: surface/alignment/profile/corridor/pipe/structure/point/section/assembly/profileview/profileviewbandset/**alignmentlabelset**/**profilelabelset**
- **createAssembly assemblyType enum values**: `UndividedCrownedRoad` / `UndividedPlanarRoad` / `DividedCrownedRoad` / `DividedPlanarRoad` / `Other` / `Railway` — required to create a road assembly; if unsure use UndividedCrownedRoad (common for municipal roads)
- **Subassemblies (pavement structure layers)**: `listStockSubassemblies{category?}` lists all available class names (Basic/Lanes/Shoulders/Daylight/CurbAndGutters etc., 12 categories, ~109 items); `createSubassembly{assemblyName, subassemblyType, side: Left|Right|Both, parameters?}` adds one.
  - **Class names must carry the `Subassembly.` prefix** (e.g. `Subassembly.BasicLane`; the plugin auto-adds it if omitted, but pass it as listed)
  - **Pavement layers**: `Subassembly.BasicLane` (single lane layer, parameters: Width/Slope/Thickness) or `Subassembly.LaneSuperelevationAOR` (superelevated lane); for multiple layers use `Subassembly.GenericPavementStructure` (multi-layer pavement) or stack several BasicLane
  - **Shoulders**: `Subassembly.ShoulderExtendAll`/`Subassembly.ShoulderMultiLayer`; **daylight (slope-to-surface)**: `Subassembly.DaylightStandard`/`Subassembly.DaylightGeneral`; **curb & gutter**: `Subassembly.UrbanCurbGutterGeneral`
  - **Typical road structure (municipal)**: pavement = BasicLane(thickness = surface + base combined), or GenericPavementStructure listing layers (e.g. 4cm fine asphalt / 6cm coarse asphalt / 32cm cement-stabilised / 30cm lime-soil); daylight with DaylightStandard(1:1); widening with LaneOutsideSuperWithWidening
  - Note: subassemblyType must come from listStockSubassemblies class names — never guess; parameters keys = subassembly parameter names (e.g. Width/Slope/Thickness)
- **Import a custom SAC part** (added 2026-08-16): `importSACSubassembly{subassemblyName, pktFilePath, insertX?, insertY?}` — imports a .pkt part file made in Subassembly Composer (e.g. non-standard granite kerb/edge/curb/tree-pit edging); after import it is used like a stock part via editAssembly / corridor regions; pktFilePath is the user-provided absolute path to the .pkt
- **AI-generate a SAC part (core! 2026-08-16)**: `buildSACSubassembly{subassemblyName, xamlContent, categoryName?, description?, atcContent?, paramsXml?}` → returns pktFilePath → import with `importSACSubassembly`. **xamlContent = SAC workflow XAML** (standard .NET workflow activities: InternalVariableDefine/FlowStep/Sequence/Point/Link/Shape etc., with x:Members defining parameters). The plugin auto-generates minimal cfg/emd/pvd templates + CreatePktFile packaging; **C3D compiles the xaml at import time, no precompiled dll needed**. Measured: APWACurbs xaml packs and imports successfully. Environment: SACRuntime DLLs in the C3D install dir; System.IO.Packaging needs WindowsDesktop 8.0
  - **SAC XAML how-to**: first read `knowledge/sac-xaml-guide.en.md` (full syntax: skeleton/activity list/expressions/flow control) + `knowledge/sac-templates/*.xaml` (4 minimal templates: EvenSlopeDitch simplest / CurbWallRadius with curves / ShoulderRoundedTarget with a target surface / PermeablePavement complex) — read a template with readFile then modify it; **ViewState layout info can be deleted** (a stripped version imports fine); the AI only needs to write the core activity logic; after generating, verify via buildSACSubassembly→importSACSubassembly, iterating on errors
- **Programmatically create a custom part** (added 2026-08-16): `createCustomSubassembly{subassemblyName, points:[{offset,elevation,code?}], links:[{pointIndices:[],code?}], shapes:[{linkIndices:[],code?}], assemblyName?, side?, insertX?, insertY?}` — define section geometry directly when there is no .pkt file (offset = lateral distance, elevation = height); links' pointIndices reference points indices, shapes' linkIndices reference links indices (a closed shape needs ≥3 edges); measured 4 points/4 links/1 shape attached to an assembly successfully. **Note: a custom part has no daylight/superelevation behaviour by default — static geometry only** (complex behaviour still needs SAC); **autoLinkCodes defaults to true** (2026-09-11): links without an explicit `code` are auto-coded — first using the owning shape's code, else `Link{n}`; **corridor surfaces/quantities rely on link codes**, so don't casually turn it off (`autoLinkCodes:false` disables); the result reports `autoCodedLinkCodes` for what was added
